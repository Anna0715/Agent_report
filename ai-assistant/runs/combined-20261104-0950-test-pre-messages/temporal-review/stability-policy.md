# test/pre 用例执行与评测稳定性

适用范围：AI 助手 test/pre 全量、专项重跑和结果评测。2026-11-04 基于本会话中用户纠正过的用例及共用执行器代码检查，落地以下改动。本次为框架加固和离线验证，未重跑线上业务、未调用真实裁判、未修改已发布报告或人工复核记录。

## 误判来源与具体处理

| 典型用例/现象 | 原来的问题 | 共用处理 |
|---|---|---|
| AA-AGG-TEST-022 | 用户要求分别计算各项目完成率，评测却额外要求跨项目总汇总 | 只评实际问题；背景事实不增添必答项，语义等价表达和可定位引用均有效 |
| AA-FU-042 | 当前能力只返回追问人所属租户，旧评测仍要求跨租户结果 | 根据 `actor_current_tenant_visible` 范围判断，不增加产品不支持的要求 |
| AA-FU-017 / AA-FU-PRE-017 | 没有具体任务，或“最近变更负责人”使用旧记录 | 保留既有专用任务刷新器，每次生成实际负责人变更并回读操作日志；发问前校验五分钟有效期 |
| AA-FU-019 / AA-FU-PRE-019 | 静态截止日期随时间失效；专用样本数被当成公司全集 | 既有六任务刷新器在每次执行时更新截止时间、状态、优先级并独立回读；新增发问前五分钟有效期校验。两条正例、四条反例只证明专用样本，不代表全公司总数 |

| 多轮、工具摘要、旧人工复核 | 只评最后一轮；工具内容静默截断；只因标签相同便复用人工结果 | 全部轮次和当次 Gold 一起评；校验逐轮覆盖和结论一致性，截断显式标记；答案、身份、问题、当前业务事实全部一致才沿用复核 |

## 已落地的执行与取证保护

`LiveAssistantAdapter` 对标准 test/pre 路径共用身份检查、会话检查、当前数据凭据及专用任务租约。CLI 新增 `--test-full` 和 `--fresh-sessions`；`--pre-full` 保持全量新会话行为。全量运行通过 `BatchSessionRecorder` 每五条完成用例回写新主会话 ID，并刷新最后不足五条的批次。延期过滤仍在这些准备动作之前。

新建会话的详情必须包含 `messages` 字段，值为 `null` 或空数组且没有历史总数；实体上下文必须与创建时计划一致。缺少历史字段、存在旧消息、错绑或无法确认预期实体时，阻止发问。无上下文的澄清场景不要求绑定实体。

标准 Trace 采集器现在按每轮实际 session/request 查找认证记录，兼容返回字段 `request_id/requestId`，并写入严格匹配凭据。一个用例跨多个会话时分别取证；预期 HTTP 权限拒绝不伪造模型 Run。Trace 补全失败保留原回答，进入证据补全流程。采集器的工具摘要仍有边界，但增加截断标记；裁判输入不再二次裁成 900 字。单例完整输入超过 200,000 字符时保留证据并待补评，不截断后强判。

执行器也取消了问答原文的 30,000 字静默截断，保留完整脱敏文本。客户端在发问调用中抛异常时，保留尝试时间、实际身份和会话，标记完成状态未知；不会丢掉记录后误称未执行，也不会自动重发。没有取得 request ID 的不确定尝试单列统计。

专用 FU017/FU019 任务以环境和任务 ID 获取本机文件租约，覆盖准备、执行、清理全程。它可以阻止本机两个批次互相改写相同任务；不能阻止另一台机器或人工改写。要解决跨主机并发，需要业务侧版本号或分布式租约，并在每轮前后回读比对。

## 当前 Gold 与 readiness.v2

有相对时间表达或历史/可变快照标记的用例，不能仅凭旧 `LIVE_VERIFIED` 标签运行或判定。标准执行要求新预检；已有专用动态刷新/受控逐轮驱动可以直接提供新 Gold。裁判检查每一轮的实际执行时间与凭据有效时间；过期或缺失的依据进入待复核，不据旧数字判错。

外部预检文件示例仅展示结构，不构成真实就绪证明：

```json
{
  "contract": "ai_assistant.readiness.v2",
  "environment": "test",
  "cases": {
    "AA-EXAMPLE": {
      "ready": true,
      "data_state": "PRECHECK_REQUIRED",
      "checked_at": "实际认证回读时间，带时区",
      "case_basis": "review_baseline.case_basis(case) 的 SHA256",
      "max_age_seconds": 300,
      "source_receipt": {"path": "source-receipt.json", "sha256": "文件字节的 SHA256"}
    }
  }
}
```

`source-receipt.json` 必须有同一 `case_id/environment/checked_at`，`source=authenticated_business_api`、`verified=true`、实际 `actor`（user_id、tenant_id，以及配置的 company_id）和非空 `facts` 对象/数组。`facts` 记录独立接口回读的对象、状态、时间窗口、范围、枚举含义及必要的完整列表。负例也可记录空集合，但要有查询范围和实际空结果；不要求为了通过而制造本应不存在的数据。

默认五分钟有效，最长十五分钟；校验文件哈希与完整用例依据，身份/问题/Gold变化或内容被修改均需重做预检。不能通过给旧文件补当前时间来升级。现有 `readiness.v1` 仅允许 FU017/FU019 已验证的专用刷新驱动把它当准备许可；旧就绪标记本身不会进入评测依据。附件预检模板已输出 v2 未就绪结构。

当前 `facts` 的业务含义仍需对应领域的采集驱动落实：通用校验能证明凭据绑定、时效和完整性，不能仅靠文件哈希证明业务数据已经进入 AI 检索索引。

## 结果状态和复核继承

| 证据情况 | 记录方式 | 报告含义 |
|---|---|---|
| 没有业务记录，或只有准备动作而没有发出问题 | `skip / not_executed` | 未执行，说明需补的条件 |
| 已发问，但缺完整回答、明确终态、当前 Gold、真实身份或本次 Trace | `skip / evidence_insufficient` | 待复核，先回查原请求 |
| 裁判初始化、调用或逐轮结构异常 | `skip / judge_error` | 待复核，保留业务证据，仅补裁判 |
| 当前业务请求有明确服务端失败终态 | `fail / execution_failure` | 执行失败，单列为执行问题 |
| 完整业务证据证明答错、漏答、编造或越权 | `fail / business_review` | 产品业务失败，写清期望、实际、差异 |
| 符合用例目标，包括预期拒绝、无结果或澄清 | `pass / business_review` | 通过 |
| 上份已保存复核为延期 | `deferred`，本轮不执行 | 延期，保留原 AI 结论与复核来源 |

发出请求数与得到确定评测结论数分别统计；待复核、未执行、延期都不进入通过/失败的有效判定分母。自动断言与业务裁判分别保留，不能把工具别名断言当成业务失败。

`ReviewBaseline` 现在还比较实际逐轮身份、执行前独立回读事实、逐轮 source_gold、写操作回读和会话实体绑定。只有凭据自身的采集时间、回读 request ID、凭据路径及会话传输 ID 不参与业务结果相等判断；嵌套业务日期、对象 ID、数量及错误均保留。旧观察格式缺少这些依据时保守重评。继承记录保留原作者、版本及时间，不能伪造一次新的人工编辑。

失败理由示例：“应返回这个项目的两条未完成主任务；实际只列出一条，漏了另一条。该任务在本轮同身份回读中仍为进行中。”具体任务名/可定位来源应从实际证据写入，不能只写“召回不足”“未达 Gold”。

## 上线执行前仍需落实的条件

1. 对缺少通用采集驱动的用例族补齐 readiness.v2 真实回读生产器；特别是聚合全集、消息时间范围和附件内容进入模型的条件。不得用旧快照或新时间戳伪装已完成。
2. 对搜索索引延迟设置只读、有上限的正向探测。超时后记录源数据已存在但索引/能力未验证，保留未执行或待补证据。单条权限拒绝前必须证明参与者能查到同一目标。
3. 跨主机并发加业务版本/共享租约，防止其他执行器和人工在问答期间改写数据。当前本机租约不能宣称解决了这个问题。
4. 补齐静态阻碍后，按已保存延期过滤做 test/pre 分开的小批真实验证，再全量运行；每次尝试保留独立会话、请求、Trace 和裁判版本，不从多次结果里只挑一次通过。

上述真实执行和报告发布不属于这次离线框架修改；没有根据本次离线检查改动已有线上结论。

## 原追问时间与消息用例复裁（2026-11-04）

`agent_evaluation.temporal_review` 供 test/pre 共用。每轮以实际用户问题的服务端 `createdAt` 为优先时间锚点，和同一 request 的认证 Trace `started_at` 交叉核对；新执行记录中的真实请求 `started_at` 也可明确标注为时间来源。不得用报告生成日期、复评日期或会话创建日期替代本次追问时间。没有原始锚点要补取证据，不能猜测。

“近期、目前、最新、仍待确认、待办”按该轮追问时已经存在的消息和有效状态验收。旧 Gold 中的九月提测日期、人力分工或未完成事项只作历史背景，不能自动变成十一月回答的必答项。“近期”没有明确天数时，不强行设为七天或三十天。明确问“8月31日之后排期变化”“原计划”“指定合并消息及原发言人”的题仍保留历史范围；不能因为消息旧就删除真实历史节点。

独立回读需保留完整分页范围、真实发言时间、正文中的会议/计划日期、编辑/撤回标记、消息 ID 和来源。按每轮追问上界排除后来消息；当前文本在追问后编辑且无原版本时，不得反向证明历史正文。当前可读也不能单独证明过去的权限，须结合原请求、当时业务上下文与正向数据条件。摘要可以选相关消息，但须记录选择规则、全量来源摘要及遗漏边界，不能静默截断成“完整事实”。

增量追问使用 `(上一条用户消息.createdAt, 本轮用户消息.createdAt]`；旧助手摘要截止日不是下界。新规则也不宽免已证实的漏答、错误状态、错误 ID、原发言人混淆或编造。历史裁判、Gold、人工复核和每次补证后的裁判都分别存档，保留新旧时间依据及其差异。

本轮落地在 `outputs/pre_temporal_rejudge_20261104/`：对指定合并报告的 26 条 pre 失败/待修复用例回读原会话与消息，只复裁其已完成的 28 轮原请求，没有重发业务问题。7 个群的 8,074 条消息按完整序号范围回读，另补读待办题的同参与者私聊；已读水位未改变。`selection.json`、`turn-time-anchors.json`、`inputs/`、`judge-raw/`、`judgments/` 以及发布验证记录分别保留选择、时间、完整输入、原始裁判及最终结果。原 test 业务证据和延期用例不重跑。
